# LoadForge Systems Engineering: Parts XXV–XXVIII

## PART XXV — COMPLETE SOURCE CODE WALKTHROUGH

This section provides a deep, line-by-line architectural breakdown of the LoadForge source tree. As a systems engineer, understanding the boundaries between components, the threading models, and memory ownership semantics is critical for maintaining and scaling LoadForge.

### C++ Engine Core

At the heart of LoadForge lies a highly concurrent, lock-minimized C++ engine designed to saturate network interfaces while accurately recording microsecond-level latency percentiles.

#### 1. Engine Orchestration
**FILE:** `engine/include/loadforge/engine.h` + `engine/src/engine.cpp`
**PURPOSE:** Orchestrates the core testing loop, tying together connection management, thread pools, and metrics.
**DEPENDENCIES:** `<atomic>`, `<functional>`, `<memory>`, `config.h`, `connection_pool.h`, `thread_pool.h`, `rate_limiter.h`, `metrics.h`
**KEY TYPES:** `class LoadEngine`
**KEY FUNCTIONS:**
- `MetricsSnapshot run()`
- `void execute_request()`
**THREADING:**
- The main thread runs the `run()` loop, blocking on the rate limiter.
- Worker threads from the `ThreadPool` execute `execute_request()`.
- A dedicated background thread runs `metrics_reporter_loop()`.
**NETWORKING:** None directly, delegates to `HttpClient`.
**ERROR HANDLING:** Catches connection pool timeouts and delegates to the metrics collector.

**Implementation Breakdown:**

The `LoadEngine` acts as the conductor. Upon construction, it immediately parses the target URL to extract the `host`, `port`, and `path`. 

```cpp
// engine/src/engine.cpp
LoadEngine::LoadEngine(const Config& config) : config_(config) {
    UrlComponents url = UrlParser::parse(config_.target_url);
    host_ = url.host;
    port_ = url.port;
    path_ = url.path + (url.query.empty() ? "" : "?" + url.query);
    
    pool_ = std::make_unique<ConnectionPool>(host_, port_, config_.max_connections);
    thread_pool_ = std::make_unique<ThreadPool>(config_.concurrency);
    limiter_ = std::make_unique<RateLimiter>(config_.requests_per_second);
    metrics_ = std::make_unique<MetricsCollector>("local", config_.test_id);
}
```

The core loop in `run()` iterates continuously until the duration is met. It computes a dynamic RPS (Request Per Second) rate to support ramp-up/ramp-down phases, acquires a token from the `RateLimiter` (blocking if we are exceeding the target RPS), and then submits an asynchronous job to the `ThreadPool`.

```cpp
// Inside LoadEngine::run()
while (!stop_requested_) {
    auto now = std::chrono::steady_clock::now();
    double elapsed = std::chrono::duration<double>(now - start_time).count();
    
    if (config_.duration_seconds > 0 && elapsed >= config_.duration_seconds) {
        break;
    }
    
    double current_rate = calculate_current_rate(elapsed);
    limiter_->set_rate(current_rate);
    
    limiter_->acquire(); // Blocks if token bucket is empty
    if (stop_requested_) break;
    
    thread_pool_->submit([this] {
        execute_request();
    });
}
```

*Interview Question: Why does `run()` dispatch work to a thread pool instead of performing asynchronous I/O with `epoll` or `kqueue`?*
*Answer: LoadForge uses thread-per-request blocking I/O (often with keep-alive connections) to simplify state tracking and accurately measure time-to-first-byte (TTFB) and DNS resolution latencies. In C++, thread pools with connection pooling can easily saturate a 10Gbps link, making the complexity of asynchronous I/O engines like `io_uring` unnecessary for standard HTTP testing workloads.*

#### 2. Socket Abstraction
**FILE:** `engine/include/loadforge/socket.h` + `engine/src/socket.cpp`
**PURPOSE:** POSIX socket wrapper that ensures safe RAII (Resource Acquisition Is Initialization) semantics.
**KEY TYPES:** `class Socket`

The `Socket` class handles the raw TCP connection. It disables copy semantics to prevent multiple handles trying to close the same file descriptor. Move semantics are implemented to allow the socket to be passed between the `ConnectionPool` and worker threads.

```cpp
// engine/include/loadforge/socket.h
class Socket {
public:
    Socket();
    ~Socket();  // closes fd
    Socket(Socket&& other) noexcept;  // move constructor
    Socket& operator=(Socket&& other) noexcept;  // move assignment
    
    // No copy
    Socket(const Socket&) = delete;
    Socket& operator=(const Socket&) = delete;
```

#### 3. Execution Pipeline
**FUNCTION:** `LoadEngine::execute_request()`
**INPUT:** None (uses member state)
**OUTPUT:** None
**CALLERS:** Worker threads in `ThreadPool`
**CALLEES:** `ConnectionPool::acquire`, `HttpClient::execute`, `MetricsCollector::record_request`

```cpp
void LoadEngine::execute_request() {
    // 1. Acquire a socket (blocks up to timeout_ms if pool is exhausted)
    Socket sock = pool_->acquire(config_.timeout_ms);
    if (!sock.is_connected()) {
        RequestResult err;
        err.success = false;
        err.error_type = "pool_timeout";
        metrics_->record_request(err);
        return;
    }
    
    // 2. Build the request structure
    HttpRequest req;
    req.method = config_.method;
    req.host = host_;
    req.port = port_;
    req.path = path_;
    req.headers = config_.headers;
    req.body = config_.body;
    if (config_.keep_alive) req.headers["Connection"] = "keep-alive";
    
    // 3. Execute the network operation
    HttpClient client;
    RequestResult result = client.execute(sock, req, config_.timeout_ms);
    
    // 4. Record latency metrics, status codes, and network errors
    metrics_->record_request(result);
    
    // 5. Return connection to pool or discard
    if (config_.keep_alive && result.response.keep_alive && result.success) {
        pool_->release(std::move(sock));
    } else {
        pool_->discard(std::move(sock)); // Socket destructor calls close()
    }
}
```

### TypeScript Controller

The TypeScript controller (Node.js/Express) is the central coordinator. It does not generate HTTP load. Its responsibilities are:
1. Validating test configurations.
2. Managing the lifecycle of distributed worker nodes.
3. Aggregating partial metrics snapshots into a global view.
4. Broadcasting real-time results via WebSockets.

#### Worker Management and Distribution
**FILE:** `controller/src/services/test-manager.ts`
When a test is triggered via `POST /api/tests`, the `TestManager` handles splitting the workload.
If the user requests 10,000 RPS and there are 4 active workers, the controller divides the configuration.

```typescript
// Conceptual code for TestManager.createTest
const workers = await workerManager.getAvailableWorkers();
const rpsPerWorker = Math.floor(testConfig.rps / workers.length);
const concurrencyPerWorker = Math.floor(testConfig.concurrency / workers.length);

const workerPromises = workers.map(worker => {
    return workerClient.startTest(worker.url, {
        ...testConfig,
        rps: rpsPerWorker,
        concurrency: concurrencyPerWorker
    });
});
await Promise.all(workerPromises);
```

#### Metrics Aggregation
**FILE:** `controller/src/services/metrics-aggregator.ts`
Every second, the controller polls each worker (or workers push via WebSocket) for their current `MetricsSnapshot`. Since percentiles (P50, P99) cannot simply be averaged, the workers send internal histogram bins, or the controller uses a simplified weighted average for real-time visualization (with the final report calculated accurately from HDR histograms).

## PART XXVI — COMPLETE REQUEST WALKTHROUGH

Let us trace a single HTTP request through the entire system from the moment the user clicks the button.

### Phase 1: User Intent to Worker Invocation
1. **Frontend Initiation**: The user clicks "Start Test" on the React Dashboard. `TestForm.tsx` collects the target URL, duration, and RPS, packaging it into a JSON payload.
2. **REST API**: A `fetch` request is sent to `POST /api/tests` on the Node.js Controller.
3. **Controller Validation**: Express router invokes `TestManager.createTest()`. The configuration is validated. A unique `test_id` is generated.
4. **Distribution**: The controller queries its `WorkerManager` for healthy worker nodes. It splits the RPS across the workers.
5. **Worker Start**: The controller issues an HTTP request to each worker's `WorkerServer` at `POST /start`.

### Phase 2: Worker Engine Initialization
6. **Engine Spawn**: The C++ worker receives the configuration and constructs a `LoadEngine`.
7. **Thread Allocation**: The `ThreadPool` allocates threads. The `ConnectionPool` initializes an empty queue. The `RateLimiter` initializes its token bucket timer.
8. **Test Loop**: The `run()` loop begins in the main thread. It blocks on `RateLimiter::acquire()`.

### Phase 3: The Lifecycle of a Request
9. **Dispatch**: The rate limiter grants a token. The main thread calls `ThreadPool::submit()`, placing a closure in the thread pool queue.
10. **Thread Pickup**: A worker thread wakes up via a condition variable and pops the job from the queue. It executes `LoadEngine::execute_request()`.
11. **Connection Acquisition**: The thread calls `pool_->acquire()`. If a keep-alive socket is available, it is returned immediately. Otherwise, a new `Socket` object is instantiated.
    - `getaddrinfo()` translates the hostname.
    - `socket()` creates an OS file descriptor.
    - `connect()` initiates the TCP 3-way handshake.
12. **Serialization**: `HttpRequest.serialize()` formats the HTTP/1.1 payload (e.g., `"GET /api/users HTTP/1.1\r\nHost: localhost\r\n\r\n"`).
13. **Data Transmission**: `Socket::send()` issues a `write()` system call, pushing the buffer to the OS network stack.
14. **Waiting for Response**: `Socket::recv()` calls `poll()` with a timeout. The OS suspends the thread until the NIC receives the response and the kernel places it in the socket read buffer.
15. **Data Reception & Parsing**: `recv()` reads the bytes. `HttpParser::parse()` processes the status line, headers, and body size.
16. **Metric Recording**: The elapsed time is calculated. `MetricsCollector::record_request(result)` is called.
    - An atomic counter increments `total_requests_`.
    - The response latency is pushed into the `Histogram` bins.
    - The HTTP status code is tracked in a map.
17. **Cleanup**: The `Socket` is returned to the `ConnectionPool` via `release()` (if `keep-alive` is respected) or safely closed.

### Phase 4: Aggregation and Display
18. **Worker Snapshot**: The background thread in `LoadEngine` calls `snapshot()` every second, calculating the current P50/P99 from the `Histogram`.
19. **Controller Polling**: The Controller requests `/api/metrics` from all workers, merging the arrays.
20. **WebSocket Broadcast**: The aggregated metrics are emitted via `ws.broadcast('metrics_update', data)`.
21. **React State Update**: `useWebSocket` hook in the browser captures the message and updates `metricsHistory`.
22. **Chart Render**: Recharts re-renders the Latency, RPS, and Error graphs, visually updating the dashboard for the user.

## PART XXVII — COMPLETE TEST WALKTHROUGH

Let us simulate a high-capacity test run.

**Configuration:**
- **Target**: `http://localhost:8080/api/users`
- **RPS**: 10,000
- **Duration**: 30 seconds
- **Workers**: 4
- **Concurrency**: 50 per worker (200 total)
- **Timeout**: 5 seconds
- **Ramp-up**: 5 seconds

### 1. Pre-flight & Ramp-up (T = 0 to 5s)
The controller splits the workload: **2,500 RPS** and **50 threads** per worker.
At T=1s, the `LoadEngine` calculates a current rate of `2500 * (1/5) = 500 RPS`. The rate limiter allows 500 requests per second. The connection pools are initially empty, so the thread pools rapidly create 50 connections per worker.

### 2. Steady State (T = 5 to 25s)
The rate limiter operates at a full 2,500 RPS per worker.
Connections are kept alive. The `pool_->active_count()` metric stabilizes near 50. Threads spend the majority of their time blocked on `poll()` inside `Socket::recv()`.
The controller aggregates `10,000 RPS` exactly. The latency charts show a steady P50 of 4ms and P99 of 12ms. CPU utilization on the workers stabilizes at ~40%.

### 3. Ramp-down & Completion (T = 25 to 30s)
Assuming a 5-second ramp-down, the RPS gradually decreases. At T=30s, `run()` breaks its loop. `ThreadPool::shutdown()` joins all worker threads. The connections are destroyed when the `ConnectionPool` is destructed, issuing `FIN` packets to the target server.

### 4. Final Aggregation
The controller queries the final comprehensive histogram from all workers, persists the final JSON report to the PostgreSQL database, and signals the frontend that the test state is `COMPLETED`.

## PART XXVIII — FAILURE WALKTHROUGHS

Systems engineering is fundamentally about understanding and mitigating failure. Here is how LoadForge behaves during major failure scenarios.

### Scenario 1: Target Server Crashes
- **Event**: The target server process segfaults.
- **Worker Level**: The OS sends `RST` packets for active connections. Future `connect()` calls yield `ECONNREFUSED`. `Socket::connect()` returns false.
- **Metrics**: `MetricsCollector::record_request()` receives failures. `failed_requests_` spikes. The error string `connection_refused` populates the error map.
- **System Impact**: RPS drops to 0 (successful requests). The thread pool spins rapidly as failures return instantly. The controller dashboard shows a 100% error rate. The test continues running until the duration expires, accurately recording the target's downtime.

### Scenario 2: Worker Crashes Mid-Test
- **Event**: Worker #2 runs out of memory and is killed by the OOM Killer.
- **Controller Level**: The `WorkerManager` ping fails. The worker is flagged as `OFFLINE`.
- **System Impact**: The total requested RPS of 10,000 drops immediately to 7,500. The `MetricsAggregator` merges data from the remaining 3 workers. The dashboard reflects the drop in RPS and displays a warning about a lost worker. The test completes with partial data.

### Scenario 3: Controller Crashes
- **Event**: The Node.js process encounters an unhandled exception.
- **Worker Level**: The C++ workers are autonomous. They continue generating load for the remainder of their configured duration, oblivious to the controller's demise.
- **System Impact**: The frontend WebSocket disconnects. The user is left in the dark. Once the workers finish, the final data is stored locally in their memory but is ultimately lost because no controller requests it. 

### Scenario 4: Network Connection Resets
- **Event**: A stateful firewall aggressively terminates idle TCP sessions, sending `RST`.
- **Worker Level**: A thread acquires a connection from the pool and attempts to `recv()`. The kernel returns a network error (`ECONNRESET`).
- **System Impact**: The request is logged as a failure (`connection_reset`). The socket is discarded rather than returned to the pool. On the next request loop, a new socket is initialized. The dashboard shows a minor spike in error rate.

### Scenario 5: Target Becomes Extremely Slow
- **Event**: The target database locks up, causing HTTP responses to take 4.5 seconds instead of 10ms.
- **Worker Level**: Connections remain open and block on `recv()`. The pool of 50 connections is quickly exhausted.
- **System Impact**: The `ThreadPool` queue grows massively as threads are blocked waiting for responses. The `queue_depth` metric skyrockets. Because the rate limiter continues dispensing tokens, *Coordinated Omission* occurs—LoadForge detects the slowdown, but the RPS plummets because there are no available threads to initiate new connections. The user sees a massive spike in P99 latency and a corresponding drop in RPS.

### Scenario 6: Load Generator Cannot Achieve Requested RPS
- **Event**: The user configures 500,000 RPS on a single, low-spec VM.
- **Worker Level**: The worker CPU hits 100%. The thread pool cannot keep up with the rate limiter. Context switching overhead consumes all CPU cycles.
- **System Impact**: The actual output RPS is far below the configured RPS. The worker's `worker_cpu_percent` metric hits 100.
- **Diagnosis**: The results are fundamentally **unreliable**. The bottleneck is the test apparatus, not the target system. The user must scale horizontally by adding more workers.

### Scenario 7: Database Becomes Unavailable
- **Event**: The PostgreSQL instance storing test history restarts.
- **Controller Level**: Database queries fail. The global `isDbConnected` flag toggles to false.
- **System Impact**: The controller gracefully degrades. In-flight tests continue operating perfectly via WebSockets. However, upon completion, the final report cannot be saved and is held in memory. If the controller restarts before the database returns, the data is lost.

### Scenario 8: Prometheus Becomes Unavailable
- **Event**: The Prometheus sidecar container crashes.
- **System Impact**: Zero impact on test execution. The LoadForge controller's `/metrics` endpoint simply goes unscraped. Grafana dashboards will show gaps in time-series data, but the LoadForge React dashboard (driven by WebSockets) remains perfectly functional. The canonical test report in PostgreSQL is entirely unaffected.
