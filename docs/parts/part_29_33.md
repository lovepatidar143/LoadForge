# PART XXIX — ARCHITECTURAL DECISIONS (ADRs)

In systems engineering, every decision is a trade-off. There are no perfect solutions, only optimal balances between latency, throughput, complexity, and maintainability. This section documents the core architectural decisions that define LoadForge.

### ADR-001: C++ for the Load Engine
**Context:** We need a systems language for the performance-critical HTTP load generator. It must be capable of saturating a network link with minimal CPU overhead.
**Options:** C, C++, Go, Rust, Java
**Decision:** C++17
**Reason:** 
- Near-metal performance without runtime overhead or unpredictable latency spikes.
- Direct, unadulterated access to POSIX sockets, `poll()`, and OS-level system calls.
- Standard library components (`std::thread`, `std::atomic`, `std::chrono`) for portable, low-level concurrency.
- Zero garbage collector (GC) pauses, which is absolutely critical for accurate microsecond-level latency measurement.
- STL containers and smart pointers provide a safety net over raw C.
**Trade-offs:**
- Significantly harder to write safely than Go or Rust; manual memory management and lifetime tracking are required.
- No built-in HTTP library (necessitating a custom HTTP parser and client).
- More complex build system (CMake).
- Lack of memory safety guarantees (buffer overflows or use-after-free are possible if not careful).
**Future alternatives:** Rust (for strict memory safety without GC), Go (for simpler concurrency, though GC pauses would require careful mitigation like object pooling).

### ADR-002: Node.js for the Controller
**Context:** We need a runtime for the orchestration layer, which coordinates distributed workers, aggregates metrics, and serves the dashboard.
**Options:** Python, Node.js, Go, Java
**Decision:** Node.js with TypeScript
**Reason:**
- Event-driven, non-blocking I/O is perfect for coordination, where the workload is I/O-bound rather than CPU-bound.
- Excellent, battle-tested WebSocket support (e.g., `ws` package).
- TypeScript provides strong compile-time type safety.
- Massive npm ecosystem for rapid development (Express, pg, ws, prom-client).
- Allows context-switching free development by sharing the same language (TypeScript) with the frontend.
**Trade-offs:**
- Single-threaded event loop means CPU-heavy metric aggregations could block the loop.
- Less structurally type-safe at runtime compared to Go or Rust.
**Future alternatives:** Go (if the controller becomes highly CPU-bound from complex percentile aggregations across thousands of workers).

### ADR-003: React for the Dashboard
**Context:** We need a real-time dashboard for metrics visualization.
**Decision:** React + TypeScript + Vite + Tailwind CSS + Recharts
**Reason:** Component-based model allows for reusable UI elements. Hooks simplify complex WebSocket state management. Recharts provides fast, SVG-based charting. Tailwind allows rapid, maintainable styling without context-switching to CSS files.

### ADR-004: HTTP/JSON for Worker Communication (not gRPC initially)
**Context:** Need a communication protocol between the Node.js controller and the C++ workers.
**Decision:** HTTP/JSON initially, with a planned gRPC upgrade path.
**Reason:** Integrating gRPC into a C++ build introduces massive dependencies (Protobuf, gRPC core) which can add 30+ minutes to the build time. HTTP/JSON uses the same code paths we already built for the HTTP client, reducing complexity and allowing simpler debugging (e.g., via `curl`).
**Trade-offs:** Significantly less efficient parsing, no bidirectional streaming, and no automatic type generation.
**Future:** Upgrade to gRPC for efficient, binary-packed streaming metrics and strict type safety across language boundaries.

### ADR-005: PostgreSQL for Persistence
**Decision:** PostgreSQL for state and time-series history due to ACID compliance and JSONB.
### ADR-006: WebSockets for Real-Time Updates  
**Decision:** WebSockets for bidirectional low-latency metric streaming to UI.
### ADR-007: poll() for I/O Multiplexing (not epoll)
**Decision:** `poll()` for portability (macOS/Linux) in the v1 engine.
### ADR-008: Token Bucket for Rate Limiting
**Decision:** Atomic token bucket for smooth RPS distribution.
### ADR-009: Logarithmic Histogram for Latency
**Decision:** O(1) lock-free array for bucketed latency tracking.
### ADR-010: Connection Pooling with Keep-Alive
**Decision:** Connection pool to avoid TIME_WAIT and 3-way handshake overhead.
### ADR-011: Thread Pool (not one-thread-per-request)
**Decision:** Fixed thread pool mapping directly to core count for CPU cache locality.
### ADR-012: Local Metric Aggregation
**Decision:** Workers aggregate locally and flush periodically to prevent network saturation.
### ADR-013: Prometheus for Observability
**Decision:** Embedded `/metrics` endpoint for system health visibility.
### ADR-014: Docker for Deployment
**Decision:** Multi-stage Docker builds to encapsulate C++ dependencies.
### ADR-015: No HTTPS in Raw Socket Client
**Decision:** Bare HTTP/1.1 accepted as limitation for MVP to reduce TLS integration overhead.

## PART XXXI — INTERVIEW HANDBOOK

### C++ Questions
Beginner: What is RAII? How does it apply to LoadForge's Socket class?
*Answer:* RAII ties resource lifecycle to object lifetime. Socket calls socket() in constructor, close() in destructor. Prevents fd leaks.
Intermediate: Explain move semantics. Why does the Socket class need a move constructor?
*Answer:* File descriptors can't be copied. Move transfers the fd int and nullifies the source to avoid double close().
Advanced: How do atomic operations in the Histogram avoid data races? What memory ordering is needed?
*Answer:* fetch_add with memory_order_relaxed ensures lock-free concurrent increment without costly CPU synchronization barriers.
Expert: If you wanted to eliminate all locks from the metrics path, how would you redesign it?
*Answer:* Thread-local histograms that are asynchronously read by a reporter thread, avoiding cache invalidation.

### OS Questions
Beginner: What is a process vs a thread? Why does LoadForge use threads not processes?
*Answer:* Threads share memory space, making metric aggregation trivial compared to IPC between processes.
Intermediate: What is a context switch? Why does LoadForge's thread pool size matter?
*Answer:* Saving/loading registers. 10k threads = scheduler thrashing. Pool size = CPU cores = max efficiency.
Advanced: Explain the file descriptor limit. How does it constrain LoadForge's max connections?
*Answer:* ulimit -n limits open sockets. Must tune kernel to allow >65k sockets.
Expert: Design a scheme to handle 1 million concurrent connections on a single machine.
*Answer:* epoll/kqueue, kernel tuning (tcp_tw_reuse, somaxconn), user-space TCP stack (DPDK/Seastar).

### Networking Questions
Beginner: What is TCP? Why does HTTP use TCP?
*Answer:* Reliable, ordered delivery stream. HTTP needs to ensure full headers/bodies are intact.
Intermediate: Explain the three-way handshake. What is the cost?
*Answer:* SYN, SYN-ACK, ACK. Costs 1 full RTT latency. We use keep-alive to skip this.
Advanced: What is TIME_WAIT? How does it affect load testing?
*Answer:* Socket lingering state. Exhausts ephemeral ports. Connection pooling is essential.
Expert: How would you detect and handle SYN flood conditions in a load tester?
*Answer:* Separate connection latency from TTFB (Time to First Byte). Alert on connection timeouts.

## PART XXXII — PROJECT DEFENSE

### 30-Second Pitch
"LoadForge is a distributed HTTP load-testing platform I built from scratch. The engine is C++ using raw POSIX sockets, connection pooling, and token-bucket rate limiting. A Node.js controller orchestrates multiple workers and streams metrics via WebSocket to a React dashboard. I built every layer — from the TCP socket wrapper to the histogram that calculates P99 latency."

### Hostile Questions Preparation
- "Did you actually build this?" → Explain the specific rate limiter deadlock you encountered and how memory ordering fixed it.
- "Why C++?" → Zero GC pauses ensures the latency measured is the target's, not the tool's.
- "Why not Go?" → Go's scheduler introduces microsecond jitter.
- "How do you know numbers are accurate?" → steady_clock usage and coordinated omission mitigation.
- "Can generator become bottleneck?" → Yes, monitored via local CPU usage self-reporting.
- "How do you calculate P99?" → O(1) log bucket walking algorithm.
- "What happens if worker dies?" → Controller heartbeat detects drop, reallocates load.
- "How would you generate 1M RPS?" → Multi-node distributed cluster, kernel tuning, bypassing loopback.
- "What would you change with more time?" → TLS, scripting engine, t-digest merging.

## PART XXXIII — LIMITATIONS AND FUTURE WORK

### Current Limitations
- No HTTPS: raw socket client doesn't implement TLS.
- No HTTP/2 or HTTP/3.
- Worker server is minimal (placeholder HTTP implementation).
- JSON parser is basic (parse() returns empty dict mostly).
- No scripting/scenario support (only static paths).
- No authentication on API.
- Single controller (SPOF).
- Percentile aggregation across workers uses max (not mathematically correct).

### Scalability Limitations
- Single controller bottleneck for WebSocket fanout.
- In-memory test state lost on controller restart.
- Database writes synchronous.
- No dynamic connection pool sizing optimization.

### Future Work
- HTTPS/TLS: integrate OpenSSL or BoringSSL, wrap fd in SSL*.
- HTTP/2: multiplexed streams, HPACK header compression logic.
- HTTP/3: QUIC implementation over UDP.
- Scripting: Embed LuaJIT or V8 for complex scenarios.
- Adaptive load: AI/PID loop to auto-find maximum RPS before failure.
- Worker auto-discovery: Gossip protocol or mDNS.
- Real gRPC: Replace HTTP/JSON for high-efficiency binary RPC.
- Distributed histogram merging: Implement t-digest mathematically.
