# LoadForge Systems Engineering: Parts IV - VIII

## PART IV — BUILDING THE FIRST LOAD GENERATOR (Chapters 97-110)

### Chapter 97: Repository Setup

Before writing a single line of C++ for a high-performance system like LoadForge, defining a solid repository structure is non-negotiable. Systems software is intricate, managing networking, threading, build configurations, and tests. A monolithic directory quickly becomes unmaintainable. 

Here is the repository structure we employ for LoadForge:

```text
LoadForge/
├── engine/              # Core C++ high-performance load generation engine
│   ├── src/             # Implementation files (.cpp)
│   ├── include/         # Public headers (.h)
│   └── tests/           # CTest/GTest unit tests
├── controller/          # Go-based distributed cluster controller
├── frontend/            # React/TypeScript web interface for test visualization
├── docker/              # Dockerfiles for containerization
├── scripts/             # Deployment and utility scripts (bash/python)
├── docs/                # Architecture diagrams and API documentation
├── proto/               # gRPC Protobuf definitions for inter-process communication
└── CMakeLists.txt       # Root build configuration
```

**Why this structure?**
LoadForge is a distributed system, not just a standalone executable. The `engine/` directory is written in C++ for raw speed, while the `controller/` might be in Go for superior concurrency and web handling. The `proto/` directory serves as the contract between these disparate components. By separating the codebase logically by domain and language, we ensure that the C++ build system does not conflict with Go modules or npm packages.

### Chapter 98: Build System (CMake)

For C++ projects, CMake is the de facto standard. It provides a platform-independent way to describe the build process.

Here is the root `CMakeLists.txt` philosophy used in LoadForge. We enforce the C++17 standard to utilize features like `std::optional`, structured bindings, and enhanced threading support.

```cmake
cmake_minimum_required(VERSION 3.10)
project(LoadForgeEngine VERSION 0.1.0 LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_EXTENSIONS OFF)

# Strict warnings to catch bugs early
set(CMAKE_CXX_FLAGS "${CMAKE_CXX_FLAGS} -Wall -Wextra -Wpedantic")

# Include directories
include_directories(include)

# Source files
set(SOURCES
    src/main.cpp
    src/engine.cpp
    src/socket.cpp
    src/thread_pool.cpp
    src/rate_limiter.cpp
    src/metrics.cpp
    src/histogram.cpp
    src/http_parser.cpp
)

add_executable(loadforge ${SOURCES})
target_link_libraries(loadforge pthread)
```

**Compiler Flags:**
- `-Wall -Wextra`: Enables a comprehensive set of warnings.
- `-Wpedantic`: Ensures strict ISO C++ compliance, preventing the use of compiler-specific extensions.

**Linking:**
`target_link_libraries(loadforge pthread)` is crucial. LoadForge spawns multiple threads to handle concurrent socket connections. Without linking the POSIX thread library (`pthread`), the linker will fail to resolve `std::thread` symbols on Linux systems.

**Building:**
```bash
mkdir build && cd build
cmake ..
make -j$(nproc)
```
This out-of-source build keeps the source tree clean.

### Chapter 99-100: First C++ Executable and CLI

The entry point of the LoadForge engine is `src/main.cpp`. It acts as the orchestrator: parsing user intents, constructing the configuration, instantiating the engine, and printing the results.

```cpp
#include "loadforge/engine.h"
#include <iostream>

using namespace loadforge;

int main(int argc, char* argv[]) {
    std::cout << "LoadForge v0.1.0\n";
    
    Config config;
    config.target_url = "http://example.com/";
    config.duration_seconds = 1;
    config.requests_per_second = 10;
    
    for (int i = 1; i < argc; ++i) {
        std::string arg = argv[i];
        if (arg == "--url" && i + 1 < argc) config.target_url = argv[++i];
        if (arg == "--duration" && i + 1 < argc) config.duration_seconds = std::stoi(argv[++i]);
        if (arg == "--rate" && i + 1 < argc) config.requests_per_second = std::stoi(argv[++i]);
    }
    
    LoadEngine engine(config);
    engine.set_metrics_callback([](const MetricsSnapshot& s) {
        std::cout << "RPS: " << s.current_rps << " | Active conn: " << s.active_connections << "\n";
    });
    
    MetricsSnapshot final_metrics = engine.run();
    std::cout << "Latency P99 (ms): " << final_metrics.latency_p99_ms << "\n";
    return 0;
}
```
*Code from `src/main.cpp`*

We avoid heavy CLI parsing libraries (like `boost::program_options`) to keep dependencies minimal. A simple loop suffices for the core arguments: `--url`, `--rate`, `--duration`.

### Chapter 102-103: TCP Socket Connection

To generate load, we must talk to the network. Abstractions like `libcurl` are too heavy; we need raw POSIX sockets for maximum control.

```cpp
bool Socket::connect(const std::string& host, int port, int timeout_ms) {
    struct addrinfo hints{}, *res;
    hints.ai_family = AF_UNSPEC;
    hints.ai_socktype = SOCK_STREAM;
    
    if (getaddrinfo(host.c_str(), std::to_string(port).c_str(), &hints, &res) != 0) return false;
    
    fd_ = ::socket(res->ai_family, res->ai_socktype, res->ai_protocol);
    
    int opt = 1;
    setsockopt(fd_, IPPROTO_TCP, TCP_NODELAY, &opt, sizeof(opt));
    
    int flags = fcntl(fd_, F_GETFL, 0);
    fcntl(fd_, F_SETFL, flags | O_NONBLOCK);
    
    int rc = ::connect(fd_, res->ai_addr, res->ai_addrlen);
    // ... handling non-blocking connect with poll()
}
```
*Code excerpt from `src/socket.cpp`*

**Key Concepts:**
1. **`getaddrinfo`**: Resolves the hostname to an IP address (DNS).
2. **`TCP_NODELAY`**: Disables Nagle's algorithm. Nagle delays sending small packets to batch them. In load testing, we want zero artificial delays!
3. **Non-blocking `connect()`**: Calling `connect()` on a blocking socket might hang indefinitely if the server drops packets. We set `O_NONBLOCK`, call `connect()`, and if it returns `EINPROGRESS`, we use `poll()` to wait for the socket to become writable (indicating connection success) up to `timeout_ms`.
4. **RAII**: The `Socket` class destructor calls `::close(fd_)`. This guarantees no file descriptor leaks, even if an exception is thrown. Move semantics transfer ownership of the `fd_`.

### Chapter 104-105: Sending HTTP Request and Receiving Response

An HTTP request is merely a formatted text string sent over a TCP socket.

```cpp
std::string HttpRequest::serialize() const {
    std::ostringstream oss;
    oss << method << " " << path << " HTTP/1.1\r\n";
    oss << "Host: " << host << "\r\n";
    for (const auto& kv : headers) {
        oss << kv.first << ": " << kv.second << "\r\n";
    }
    if (!body.empty()) {
        oss << "Content-Length: " << body.size() << "\r\n";
    }
    oss << "\r\n" << body;
    return oss.str();
}
```
*Code from `src/http_parser.cpp`*

**The wire format:** Every line must end with `\r\n` (CRLF). The headers and body are separated by an empty line `\r\n\r\n`. 

### Chapter 106: Response Parsing

Receiving is harder than sending. TCP is a stream protocol; `recv()` might return 10 bytes, 100 bytes, or the whole response. 

The `HttpParser::parse` method handles this:
1. Locates `\r\n\r\n` to split headers and body.
2. Parses the status line (`HTTP/1.1 200 OK`).
3. Extracts headers, paying special attention to `Content-Length` and `Transfer-Encoding: chunked`.
4. Checks `Connection: keep-alive` to know if the socket can be reused.

### Chapter 107: Measuring Request Latency

Timing is everything in a load generator.

```cpp
// Conceptual timing logic inside execute_request
auto start = std::chrono::steady_clock::now();
socket.connect(...);
auto connect_time = std::chrono::steady_clock::now();

socket.send(req_str);
auto send_time = std::chrono::steady_clock::now();

// ... receive headers ...
auto ttfb = std::chrono::steady_clock::now(); // Time To First Byte

// ... receive full body ...
auto end = std::chrono::steady_clock::now();
```

We use `std::chrono::steady_clock` because it is strictly monotonic. Unlike `system_clock`, it is unaffected by NTP time adjustments. If the system clock shifts backwards by an hour during a test, `steady_clock` ensures our latency measurements don't yield negative values.

### Chapter 108-109: Error Handling and Timeouts

Load testing implies failure. When the target server crumbles, the load generator must survive to report it.

Errors are classified stringently:
- `connect_timeout`: Server didn't respond to SYN.
- `read_timeout`: `poll()` timed out waiting for data.
- `connection_refused`: Server actively rejected (RST).
- `connection_reset`: Connection dropped mid-flight.

## PART V — CONCURRENCY (Chapters 111-124)

### Chapter 111: Why One Request at a Time Is Insufficient

A sequential loop sending one request, waiting for the response, and repeating is fatally flawed.
If a server has a latency of 50ms, a single sequential thread can achieve a maximum of 20 Requests Per Second (1000ms / 50ms). 

To achieve 1,000 RPS at 50ms latency, Little's Law ($L = \lambda W$) states we need an average of 50 concurrent requests in flight. Concurrency is mandatory.

### Chapter 112-113: Concurrent Requests and Threads

We could spawn a new `std::thread` for every request. However, thread creation costs ~50-100μs, and each thread consumes ~2MB of stack space. Spawning 10,000 threads for 10,000 requests will exhaust memory and crash the OS kernel scheduler.

### Chapter 114: Thread Pool

The solution is a Thread Pool: a fixed number of pre-allocated threads waiting for work.

```cpp
ThreadPool::ThreadPool(size_t num_threads) {
    for (size_t i = 0; i < num_threads; ++i) {
        workers_.emplace_back([this] {
            while (true) {
                std::function<void()> task;
                {
                    std::unique_lock<std::mutex> lock(mutex_);
                    cv_.wait(lock, [this] { return stop_ || !tasks_.empty(); });
                    if (stop_ && tasks_.empty()) return;
                    task = std::move(tasks_.front());
                    tasks_.pop();
                }
                task();
            }
        });
    }
}
```
*Code from `src/thread_pool.cpp`*

Workers sleep on a `std::condition_variable` (`cv_.wait`). When a task is pushed to the queue, `cv_.notify_one()` wakes up a thread to execute it. This avoids busy-waiting and minimizes CPU usage overhead.

### Chapter 115-118: Shared State, Race Conditions, Mutexes, Atomics

With multiple threads mutating the `MetricsCollector`, we face race conditions.
Using a `std::mutex` around every counter increment would cause massive lock contention, destroying performance.

Instead, we use `std::atomic`:
```cpp
std::atomic<uint64_t> total_requests_{0};
// ...
total_requests_.fetch_add(1, std::memory_order_relaxed);
```
Atomics compile down to hardware-level compare-and-swap (CAS) instructions (e.g., `LOCK XADD` on x86). We use `memory_order_relaxed` because we only care about the atomicity of the increment, not the synchronization of surrounding memory operations, saving precious CPU cycles.

### Chapter 119-124: Lock Contention and Backpressure

If the target server slows down, worker threads block waiting for network I/O. The task queue depth increases rapidly. This is backpressure. Monitoring the `queue_depth()` of the thread pool provides a critical health signal. If the queue grows unbounded, the generator will eventually OOM (Out of Memory).

## PART VI — HIGH-PERFORMANCE NETWORKING (Chapters 125-143)

### Chapter 125-126: Why Blocking Sockets Become Limiting

Blocking sockets tie one thread to one connection. 10,000 connections = 10,000 threads. This is the C10K problem. Non-blocking sockets (`O_NONBLOCK`) solve this, returning `EAGAIN` immediately if no data is available.

### Chapter 127-135: Event Loops, epoll, poll()

To know when a non-blocking socket is ready, we use multiplexing.
- `select()`: Legacy, limits to 1024 FDs.
- `epoll()`: Linux-specific, O(1) efficiency.
- `poll()`: Portable (macOS/Linux), no FD limit.

LoadForge's socket wrapper leverages `poll()` to achieve timeout functionality on individual operations without requiring a full async reactor pattern like ASIO, keeping the architecture straightforward yet performant.

```cpp
struct pollfd pfd;
pfd.fd = fd_;
pfd.events = POLLIN;
if (poll(&pfd, 1, timeout_ms) > 0) {
    return ::recv(fd_, buffer, len, 0);
}
```

### Chapter 136-139: Connection Manager and Keep-Alive

Establishing a TCP connection requires a 3-way handshake (SYN, SYN-ACK, ACK), taking 1 full Round Trip Time (RTT). If HTTPS is used, TLS negotiation adds 1-2 more RTTs.

To generate immense load, we *must* reuse connections via HTTP Keep-Alive. LoadForge maintains a `ConnectionPool`. When a request finishes, the `Socket` is returned to the pool's idle queue instead of being closed. The next request pops an idle socket instantly.

## PART VII — LOAD GENERATION ENGINE (Chapters 144-157)

### Chapter 144: Engine Architecture

The `LoadEngine` binds everything together.

```cpp
MetricsSnapshot LoadEngine::run() {
    auto start_time = std::chrono::steady_clock::now();
    while (!stop_requested_) {
        // ... time calculations ...
        limiter_->acquire();
        thread_pool_->submit([this] { execute_request(); });
    }
}
```
*Code from `src/engine.cpp`*

The main loop is incredibly tight. It calculates the desired rate, waits for a token from the `RateLimiter`, and then submits the request execution to the thread pool. A separate background thread runs `metrics_reporter_loop()` to emit real-time data every second.

### Chapter 146-148: Rate Limiter and Token Bucket

To maintain a precise "Requests Per Second" (RPS), we implement a Token Bucket algorithm.

```cpp
void RateLimiter::acquire() {
    std::unique_lock<std::mutex> lock(mutex_);
    while (true) {
        refill();
        if (tokens_ >= 1.0) {
            tokens_ -= 1.0;
            return;
        }
        double wait_seconds = (1.0 - tokens_) / rate_;
        cv_.wait_for(lock, std::chrono::microseconds(static_cast<int64_t>(wait_seconds * 1e6)));
    }
}
```
*Code from `src/rate_limiter.cpp`*

Tokens are added based on elapsed time (`refill()`). If no tokens are available, the thread sleeps for the exact microsecond duration needed until the next token spawns. This enables smooth, microsecond-accurate load pacing, crucial for ramp-up patterns.

## PART VIII — METRICS (Chapters 158-177)

### Chapter 158: Why Metrics Matter
Traffic without measurement is just a denial-of-service attack. Metrics transform traffic into a load test.

### Chapter 162-167: Latency Measurement and Percentiles

Averages (means) are dangerous in systems engineering. If 99 requests take 10ms and 1 takes 10 seconds, the average is ~110ms. This hides the fact that a user waited 10 seconds!

We use Percentiles (P50, P90, P99). P99 means 99% of requests were faster than this value. It exposes the long tail of latency caused by garbage collection pauses, network jitter, or lock contention on the target server.

### Chapter 174-175: Histogram Deep Dive

Storing every single latency value to sort them at the end takes too much memory (1M requests * 8 bytes = 8MB). Instead, we use a High-Dynamic-Range (HDR) Histogram.

```cpp
int Histogram::bucket_for(double value) const {
    if (value <= 1.0) return 0;
    int b = static_cast<int>(std::log(value) / std::log(1.1));
    if (b < 0) b = 0;
    if (b >= NUM_BUCKETS) b = NUM_BUCKETS - 1;
    return b;
}

void Histogram::record(double value) {
    int b = bucket_for(value);
    buckets_[b].fetch_add(1, std::memory_order_relaxed);
    // ... update min/max lock-free
}
```
*Code from `src/histogram.cpp`*

We use logarithmic buckets (base 1.1). This provides high precision at low latencies (e.g., distinguishing 1.0ms from 1.1ms) and wider bins at high latencies (e.g., 30s vs 33s), keeping the memory footprint constant (just an array of ~200 `std::atomic<uint64_t>` integers) regardless of how many requests are run.

### Chapter 177: Coordinated Omission

A critical flaw in naive load testers (like Apache Bench) is Coordinated Omission. 
If the generator waits for a slow response before sending the next one, it artificially throttles its own RPS. The slow responses "hide" the fact that requests which *should* have been sent are piling up in reality.

LoadForge solves this natively by separating the **Scheduling** (Rate Limiter in the main thread) from the **Execution** (Thread Pool). If the server slows down, the Rate Limiter keeps throwing tasks onto the thread pool queue at the configured RPS. Latency is measured from the moment the task is scheduled, thereby accurately reflecting the massive queueing delay experienced during a server brownout.
