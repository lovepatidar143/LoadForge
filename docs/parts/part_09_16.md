# PART IX — CLI (Chapters 178-186)

## Chapters 178-186: CLI Architecture, Configuration, Validation, Starting/Stopping Tests, Progress Display, Live Metrics, Final Report, Exporting Results

The Command Line Interface (CLI) is the most fundamental way to interact with the LoadForge engine. While the Node.js controller provides a distributed, web-based UI, the CLI operates directly over the C++ `LoadEngine`. This design honors a core systems programming philosophy: keep the core engine completely decoupled from the control plane. 

### CLI Architecture: The `main.cpp` Entry Point

When a user executes the `loadforge` binary from their shell, the operating system kernel performs an `execve` syscall, loading the ELF binary into memory, mapping the dynamic libraries, and jumping to the `_start` symbol which eventually calls our `main` function.

```cpp
#include "loadforge/engine.h"
#include <iostream>
#include <iomanip>

using namespace loadforge;

int main(int argc, char* argv[]) {
    std::cout << "LoadForge v0.1.0\n";
    
    Config config;
    config.target_url = "http://example.com/";
    config.duration_seconds = 1;
    config.requests_per_second = 10;
    
    for (int i = 1; i < argc; ++i) {
        std::string arg = argv[i];
        if (arg == "--url" && i + 1 < argc) config.target_url = argv[++i];
        if (arg == "--duration" && i + 1 < argc) config.duration_seconds = std::stoi(argv[++i]);
        if (arg == "--rate" && i + 1 < argc) config.requests_per_second = std::stoi(argv[++i]);
    }
    // ...
```

In the CLI architecture, parsing is kept deliberately simple. We populate a `Config` struct (defined in `loadforge/engine.h`) that maps directly to the internal C++ structures used by the `WorkerServer` and `LoadEngine`.

### Progress Display and Live Metrics

Instead of building a separate polling thread, the CLI leverages the `LoadEngine`'s built-in callback architecture. The engine guarantees that a metrics snapshot will be generated periodically (typically every 1 second). The CLI registers a lambda function to intercept this snapshot:

```cpp
    LoadEngine engine(config);
    engine.set_metrics_callback([](const MetricsSnapshot& s) {
        std::cout << "RPS: " << s.current_rps << " | Active conn: " << s.active_connections << "\n";
    });
```

Because `LoadEngine` operates using an asynchronous epoll/kqueue event loop, this callback is invoked by the engine's main loop (or a dedicated metrics thread, depending on the thread pool configuration) without blocking the hot path of network I/O.

### Final Report and Output

Once the `engine.run()` method finishes—meaning the duration has elapsed and all active connections have been drained—the CLI outputs a final report:

```cpp
    MetricsSnapshot final_metrics = engine.run();
    
    std::cout << "\nTest Complete!\n";
    std::cout << "Total Requests: " << final_metrics.total_requests << "\n";
    std::cout << "Successful: " << final_metrics.successful_requests << "\n";
    std::cout << "Failed: " << final_metrics.failed_requests << "\n";
    std::cout << "Latency P50 (ms): " << final_metrics.latency_p50_ms << "\n";
    std::cout << "Latency P99 (ms): " << final_metrics.latency_p99_ms << "\n";
    
    return 0;
}
```

**Interview Question**: *Why does `engine.run()` return a `MetricsSnapshot` instead of forcing the user to aggregate metrics themselves?*
*Answer*: The engine possesses the exact thread-local histograms. If the CLI had to aggregate them, it would require acquiring locks across the engine's internal thread pool, potentially introducing contention at the exact moment the test finishes. Returning a final aggregated snapshot allows the engine to locklessly reduce the thread-local metrics into a single struct before tearing down the worker threads.

# PART X — NODE.JS CONTROLLER (Chapters 187-199)

## Chapter 187: Why a Controller Exists

While the CLI is perfect for a single machine, a realistic load testing scenario demands distributed traffic generation. A single machine is limited by:
1. **CPU Exhaustion**: Parsing JSON and managing TLS handshakes takes cycles.
2. **Ephemeral Port Exhaustion**: A machine only has ~65,535 ports. Even with `SO_REUSEADDR`, you are bottlenecked by the OS's TCP stack.
3. **Network Bandwidth**: 10 Gbps is easily saturated by large payloads.

The **Controller** acts as the orchestration layer. We chose Node.js for the controller because Node's architecture (V8 + libuv) is fundamentally built around non-blocking I/O and an event-driven model. The controller does *no CPU-heavy work*; it merely coordinates HTTP requests to workers, multiplexes WebSockets to browsers, and streams JSON metrics into PostgreSQL. 

## Chapters 188-189: Controller Architecture and Node.js Runtime

The controller uses an Express HTTP server coupled with a WebSocket server (`ws` library). 

```text
+----------------+      +-------------------+      +------------------+
|                |      |                   |      |                  |
|  React UI      |<====>|  WebSocket (ws)   |<====>|  Metrics Service |
| (Dashboard)    |      |  (Node.js)        |      |                  |
|                |      |                   |      |                  |
+----------------+      +---------+---------+      +--------+---------+
                                  |                         |
                                  v                         v
                        +---------+---------+      +--------+---------+
                        |                   |      |                  |
                        | Express REST API  |      | PostgreSQL (pg)  |
                        |                   |      |                  |
                        +---------+---------+      +------------------+
                                  |
                                  v
                        +-------------------+
                        |                   |
                        |  Worker Clients   |
                        |  (Distributed)    |
                        +-------------------+
```

Node's event loop is single-threaded. This is an advantage here: we can mutate in-memory state (like aggregating metrics) without needing mutexes, spinlocks, or dealing with race conditions that C++ or Go would require.

## Chapters 190-192: TypeScript, API Design, Configuration Validation

TypeScript ensures that the data structures flowing from the UI to the controller to the C++ workers remain strictly typed. The REST API exposes routes to manage the test lifecycle:
* `POST /api/tests` - Create a test
* `POST /api/tests/:id/start` - Dispatch test to workers
* `POST /api/tests/:id/stop` - Halt workers

## Chapters 193-195: Test Lifecycle, Worker Management, and State

The test lifecycle transitions through state machines: `pending -> running -> completed/failed/cancelled`.
The `WorkerManager` keeps track of workers in-memory. Workers register themselves via a POST request, and the manager continually polls them (heartbeats).

## Chapter 196: WebSocket Architecture

To provide a real-time dashboard, the controller uses WebSockets to stream metrics. When the `MetricsAggregator` produces a new combined snapshot, it is piped to the `WebSocketHandler`:

```typescript
export class WebSocketHandler {
  private wss: WebSocketServer;

  constructor(server: http.Server) {
    this.wss = new WebSocketServer({ server, path: '/ws' });
  }

  broadcast(event: string, data: any): void {
    const message = JSON.stringify({ event, data });
    this.wss.clients.forEach((client) => {
      if (client.readyState === WebSocket.OPEN) {
        client.send(message);
      }
    });
  }
}
```

The stringification of JSON happens once per broadcast, not per client, saving CPU cycles on the event loop.

## Chapters 197-199: Error Handling, Controller Testing

If the database goes down mid-test, the controller degrade gracefully. It caches the test timeline in memory up to a limit, ensuring that real-time UI users continue to see data even if persistence fails.

# PART XI — DISTRIBUTED WORKERS (Chapters 200-223)

## Chapters 200-201: Why One Worker Isn't Enough, Horizontal Scaling

At an OS level, every TCP connection is uniquely identified by a 4-tuple: `(Source IP, Source Port, Dest IP, Dest Port)`. Because the Destination IP/Port (the target server) is fixed, the OS must allocate a unique Source Port for every outbound request. 
The ephemeral port range (e.g., `32768` to `60999` on Linux) dictates how many concurrent connections can exist. When ports run out, the `connect()` syscall returns `EADDRNOTAVAIL`. To scale beyond this, you must distribute the load across multiple physical network interfaces (multiple workers).

## Chapters 202-208: Distributed Architecture, Assignment, Work Distribution

When the controller receives a request to start a test at 10,000 RPS, it queries the `WorkerManager`. If 4 workers are healthy, the work is partitioned: 2,500 RPS per worker.

*Worker Identity*: Each C++ worker generates a UUID at startup and POSTs it to the controller.
*Health Checking*: The controller expects the worker to respond to `/api/health`. If 3 consecutive heartbeats fail, the worker is marked offline.

## Chapters 209-213: gRPC, Protocol Buffers, Serialization

While LoadForge currently uses HTTP/JSON for controller-worker RPC (for minimal dependencies), the architecture is fundamentally designed around Protocol Buffers. 

Look at `proto/loadforge.proto`:

```protobuf
message MetricsSnapshot {
  string worker_id = 1;
  string test_id = 2;
  int64 timestamp_ms = 3;
  
  uint64 total_requests = 4;
  double current_rps = 9;
  
  LatencyHistogram latency = 14;
}
```

Protobuf is binary and relies on schema-based varint encoding. A JSON payload with field names `{"total_requests": 500}` takes ~22 bytes. In Protobuf, field `4` encoded with a varint takes ~2 bytes. When streaming thousands of metrics, Protobuf drastically reduces memory bandwidth and garbage collection overhead.

## Chapters 214-222: Network Partitions, Failure Detection

If a worker is partitioned, the controller aggregates metrics from the remaining 3 workers. The total RPS drops from 10,000 to 7,500. The dashboard reflects this instantly. Once the test completes, the Controller issues a broad cancellation. The partitioned worker, upon regaining connectivity, will realize its test ID is stale and auto-abort.

# PART XII — DISTRIBUTED METRICS (Chapters 224-233)

## Chapters 224-233: Local Aggregation vs Per-Request

If you run 4 workers at 10,000 RPS, generating a network packet or DB row for every single request (40,000 times a second) would DDOS your own metrics infrastructure.
Instead, LoadForge employs **Local Aggregation**. The C++ workers maintain thread-local HDR Histograms (High Dynamic Range) that record latency. Every 1 second, these are flushed into a `MetricsSnapshot` and polled by the controller.

In `controller/src/services/metrics-aggregator.ts`, we see the merging logic:

```typescript
      for (const s of snapshots) {
        merged.totalRequests += s.totalRequests;
        merged.currentRps += s.currentRps;
        
        // Simple max across workers for percentiles
        if (s.latency) {
          merged.latency.p50Ms = Math.max(merged.latency.p50Ms, s.latency.p50Ms);
          merged.latency.p99Ms = Math.max(merged.latency.p99Ms, s.latency.p99Ms);
        }
      }
```

**Why Math.max for percentiles?**
Mathematically, you cannot average percentiles. If Worker A's p99 is 50ms, and Worker B's p99 is 150ms, taking the average (100ms) is wildly inaccurate because Worker B might have experienced massive GC pauses affecting only 1% of its requests. Taking the `Math.max` guarantees that if *any* worker saw a p99 of 150ms, we report 150ms. In systems engineering, we care about the absolute worst-case tail latency.

# PART XIII — POSTGRESQL (Chapters 234-246)

## Chapters 234-246: Schema Design, JSONB

We use PostgreSQL because of its robust MVCC (Multi-Version Concurrency Control) and `JSONB` support. The `001_create_tables.sql` file reveals:

```sql
CREATE TABLE IF NOT EXISTS tests (
  id VARCHAR(36) PRIMARY KEY,
  config JSONB NOT NULL,
  status VARCHAR(20) NOT NULL DEFAULT 'pending',
  -- aggregates --
  latency_p99_ms DOUBLE PRECISION,
  status_codes JSONB
);

CREATE TABLE IF NOT EXISTS test_timeline (
  id SERIAL PRIMARY KEY,
  test_id VARCHAR(36) REFERENCES tests(id) ON DELETE CASCADE,
  timestamp_ms BIGINT NOT NULL,
  current_rps DOUBLE PRECISION,
  latency_p99_ms DOUBLE PRECISION
);
```

By storing `config` as `JSONB`, we can dynamically add new test configuration options (like custom HTTP headers or auth tokens) without running blocking `ALTER TABLE` migrations. The `test_timeline` table is what powers the historical graphs in the dashboard.

# PART XIV — REAL-TIME DASHBOARD (Chapters 247-262)

## Chapters 247-262: React Architecture, WebSocket Integration

The frontend uses Vite + React + TypeScript.
The component tree strictly separates Presentation from Data:
* **App.tsx**: React Router setup.
* **Dashboard.tsx**: Manages the `useWebSocket` hook.
* **LatencyChart.tsx / RpsChart.tsx**: Recharts integration.

When a test is running, `Dashboard.tsx` establishes a WebSocket connection to the Controller. As the `metrics_update` event arrives, the React hook updates a rolling window array of the last 60 seconds of data. Recharts binds to this array, providing a smooth, scrolling visual representation of network degradation or latency spikes.

```tsx
// Abstracted concept from frontend/hooks/useMetrics.ts
export function useMetrics() {
  const [metrics, setMetrics] = useState<MetricsSnapshot[]>([]);
  
  useEffect(() => {
    socket.on('metrics_update', (newData) => {
      setMetrics(prev => [...prev.slice(-59), newData]); // Keep last 60 points
    });
  }, []);
  
  return metrics;
}
```

# PART XV — THREE.JS / FUTURISTIC 3D UI (Chapters 263-278)

## Chapters 263-278: Design Philosophy and WebGL

While Recharts handles 2D line graphs, systems at massive scale often benefit from topological visualization. Imagine an architectural view where each target endpoint is a node, and the load workers are surrounding it.

Using **React Three Fiber** (a React wrapper over Three.js), we can construct a 3D scene.
1. **Renderer/Scene**: The WebGL context bounds.
2. **InstancedMesh**: To render 10,000 requests per second visually, creating 10,000 distinct Mesh objects would destroy browser memory. An `InstancedMesh` allows us to draw the same geometry 10,000 times in a single draw call to the GPU, updating only a `Float32Array` of matrix positions.
3. **Particle Systems**: Request flow can be visualized as a glowing particle stream. When an HTTP 500 occurs, the particle's fragment shader turns it red.

*Note: This is a future enhancement designed to make bottleneck identification intuitive rather than purely numerical.*

# PART XVI — OBSERVABILITY (Chapters 279-290)

## Chapters 279-290: Logs, Metrics, Prometheus, Grafana

Internal observability is about testing the tester. How do we know LoadForge isn't the bottleneck?
We expose a Prometheus `/metrics` endpoint on the Node.js controller (`controller/src/prometheus/metrics.ts`):

* `loadforge_workers_active` - Are we dropping workers?
* `loadforge_requests_total{status="500"}` - High cardinality labels for granular monitoring.
* `loadforge_request_duration_ms` - A summary of how long the controller takes to process API requests.

**Prometheus Pull Model**:
Unlike the WebSockets which push data to the browser, Prometheus uses a *pull* model. Every 5 seconds, the Prometheus server executes an HTTP GET to the `/metrics` endpoint. This guarantees that if Prometheus is under heavy load, it simply polls less often, rather than the LoadForge controller getting backed up trying to push metrics to a slow consumer. The data is then visualized in Grafana, combining our internal test telemetry with Docker container stats (CPU/RAM).
